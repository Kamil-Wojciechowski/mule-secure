# Mule Secure Properties Tool (Web)

A static, browser-based port of MuleSoft's [`secure-properties-tool`](https://docs.mulesoft.com/mule-runtime/latest/secure-configuration-properties)
CLI jar. Encrypt or decrypt a value the same way `secure-properties-tool-j17.jar` does,
from a form in your browser instead of the command line.

**Live site:** enable GitHub Pages for this repo (see below) and it will be published at
`https://<your-username>.github.io/mule-secure/`.

## Why this exists, and how it works

The CLI tool runs real JCE (Java Cryptography Extension) encryption — the output has to
stay byte-compatible with what a Mule runtime expects, or the encrypted properties simply
won't decrypt in production. Rather than approximate that behavior, `crypto-core.js` in
this repo is a from-scratch reimplementation of the tool's actual encryption logic,
recovered by decompiling `secure-properties-tool-j17.jar` and reading its real key
derivation, IV handling, and padding code (`org.mule.encryption.jce.JCEEncrypter`,
`com.mulesoft.modules.configuration.properties.internal.keyfactories.SymmetricEncryptionKeyFactory`,
etc.). Notably:

- The key is used as **raw UTF-8 bytes**, with no hashing or stretching — its length must
  exactly match a size the chosen algorithm accepts.
- Unless `--use-random-iv` is set, the **IV is the first `blockSize` bytes of the key
  itself** (zero-padded if the key is shorter than one block).
- **PKCS5/PKCS7 padding is applied even in CFB and OFB modes** — despite those normally
  being treated as stream-cipher modes that need no padding, Java's SunJCE provider pads
  them anyway, and this port matches that.
- With `--use-random-iv`, the IV is randomly generated per encryption and prepended to the
  ciphertext before Base64 encoding (and stripped back off before decryption).

Everything runs client-side using two vendored, unmodified open-source crypto libraries
(see [`vendor/THIRD_PARTY_NOTICES.md`](vendor/THIRD_PARTY_NOTICES.md)) — [node-forge](https://github.com/digitalbazaar/forge)
for AES/DES/DESede/RC2, and [egoroof-blowfish](https://github.com/egoroof/blowfish) for
Blowfish. No build step, no bundler, no server, no network calls once the page has loaded.

## Scope

Both the CLI's `string encrypt`/`string decrypt` mode and `file encrypt`/`file decrypt`
mode are implemented (not `file-level` mode, which just encrypts a whole file as one opaque
blob and is rarely used in practice). In file mode, each value in a `.properties` or
`.yaml` file is encrypted/decrypted individually and wrapped as `![...]` — keys, comments,
and structure are left readable, matching the real tool's `processFileLine` behavior
(including its quirks: comments are re-emitted with normalized spacing, and a value
containing an escaped `\"` loses its surrounding quotes on the way through, exactly as the
CLI does). Decrypting a file only touches values already wrapped as `![...]`, so a file
with a mix of encrypted and plaintext values is handled correctly.

Supported algorithms are the ones that work out of the box in the real tool without
installing an extra JCE provider: **AES** (default), **Blowfish**, **DES**, **DESede**
(3DES), and **RC2** — each with all four cipher modes (**CBC**, **CFB**, **ECB**, **OFB**).
Algorithms like Camellia, CAST5, Twofish, etc. require a Bouncy Castle provider in the real
tool too, so they're out of scope here as well.

## How correctness was verified

`crypto-core.js` was validated against **184 reference vectors** generated by actually
running `secure-properties-tool-j17.jar` (every supported algorithm × every mode, several
key lengths, plaintexts spanning empty/short/exact-block-boundary/long/Unicode content),
plus decrypt round-trips and `--use-random-iv` cross-checks. All 184 matched byte-for-byte.

File mode (`file-core.js`) was separately validated against real jar output for
`.properties` and `.yaml` fixtures covering quoted/unquoted/empty values, inline and
full-line comments, comments and separators appearing inside quoted values, escaped
quotes, mixed encrypted/plaintext files, CRLF line endings, and `--use-random-iv`.

The jar itself isn't in this repo (it's MuleSoft's proprietary software, not ours to
redistribute), but the vectors/fixtures and the harness that replays them against
`crypto-core.js`/`file-core.js` are, in `test/`:

```bash
npm install
npm test
```

The same file (`crypto-core.js`) also runs a small self-test in the browser on page load
(see `app.js`) and disables the form if it ever fails, so a broken or tampered vendor
library can't silently produce wrong output.

## Deploying

This repo includes a GitHub Actions workflow (`.github/workflows/deploy.yml`) that
publishes the site to GitHub Pages on every push to `main`. One-time setup:

1. Push this repo to GitHub (already done if you're reading this there).
2. In the repo, go to **Settings → Pages** and set **Source** to **GitHub Actions**.
3. Push to `main` (or re-run the workflow from the **Actions** tab). The site will be live
   at `https://<username>.github.io/<repo>/` a minute or two later.

## Running locally

No build step — just serve the directory statically (it uses ES modules, which most
browsers block under `file://`):

```bash
python3 -m http.server 8000
# open http://localhost:8000
```

## Security notes

- Nothing is sent over the network at runtime — open DevTools → Network and encrypt
  something, or just disconnect from the internet after the page has loaded.
- This is an independent, unofficial reimplementation, not affiliated with or endorsed by
  MuleSoft or Salesforce. For anything you can't afford to get wrong, cross-check output
  against the official CLI tool too.
- Treat the page like any other place you type secrets: prefer running it locally or from
  a GitHub Pages URL you trust over pasting production keys into a random deployment.
